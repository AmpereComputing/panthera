# Furiosa microarchitecture notes

## General concepts

The Furiosa micro architecture is a relatively-standard, high-end, out-of-order, super-scalar processor. We read Arm V8 instructions out of memory, translate them into micro-ops, and then execute the micro ops (Uop). The pipeline in a speculative, out-of-order processor is generally considered to be split into 2 distinct parts, the frontend and backend. The front end produces a proposed series of uops, and the backend executes the uops. The backend is also responsible for figuring out if the series of uops that the frontend proposed is actually along the correct path.

## High-level flow

Big picture in a nutshell. The Instruction Cache and Fetch unit (ICF) uses its Branch Prediction Unit (BPU) to pick a possible speculative path in Virtual Address space, translates virtual address to physical addresses, fetches them, and sends the instructions to the Instruction Decode and Rename unit (IDR). The IDR decodes them into simpler micro operations (Uops), and dispatches them to either the Integer eXecution Unit (IXU) or Floating-point SIMD Unit (FSU) to schedule them. In an Out Of Order (OOO) fashion, the schedulers in the IXU and FSU pick UOPs that are ready, and issues them to appropriate hardware to actually do the operation. If the operation is a Load or a Store, the IXU asks the Load Store Unit (LSU) to perform the operation. In that case, the LSU translates the virtual addresses to physical addresses (with the help of the MMU), and does the appropriate memory operation. All of the execution hardware reports the "done" signal to Global Pipeline Control unit (GPC), which attempts to "put things back in order" by looking for uop done on the oldest of the Uops. When the GPC discovers errors in the ICF's BPU predictions of the speculative path, it tells everyone to get back on the correct path. The BPU eventually trains itself based on the updates from the GPC.

The key components in our design from top to bottom. There is a tight state machine in ICF that is making cacheline address predictions, and filling the a fifo called the Front End Queue (FEQ) with request addresses, and also sending those addresses to the BPU branch predictors. The instruction side L1 cache (IL1) is taking the request addresses from the FEQ and sending them to three different processes, the tlb, the L1 tags, and the L1 data arrays. The last part of the ICF puts it all together, and matches branch predictions to actual cachelines, perhaps restarting the predictors if it detects inconsistencies (predicted third instuction in line is a taken conditional branch, and the third instruction is not even a branch). The selected instructions are sent 8 at a time to IDR with some predecode information. Idr uses 6 decoders in a weird overlapping pattern and can take at most 5 instructions, and convert them into at most 4 micro ops (uops). The logical address of general purpose registers and vector registers are renamed into a larger number of physical gprs and vector registers in the uops. The 4 bits of condition code flags are also renamed into a pool of physical "flag" registers. The uops with their renamed resources are sent to schedulers in various units. They are selected from the schedulers in the various units (IXU, FSU, and the IDR itself) as their input resources become available. The IXU handles all loads and stores with the help of the LSU, but all memory operation go through the IXU first. As items are selected out of schedulers and either executed locally, or in the case of memory operations, in the LSU. As individual uops complete OOO, they inform the GPC which is tracking them. The GPC tracks the uops being "done" in an in-order fashion. As the oldest uops in the machine get their done indication, the gpc "commits" them, and updates resources that were mapped to physical registers to back to the "committed" logical resource they originally came from. Uops that also mark the last uop in an instruction are specially noted, and update the running notion of the program counter. If a uop represents a Store operation, they are finally allowed to actually update memory in a process called retirement. As the branch execution sub unit of the IXU executes branch instructions it may find that the BPU guessed wrong about the direction of the branch or the target address of the branch. If so, it reports that to the GPC, which then tells everyone else. Uops in the machine that are younger than the branch are flushed and ICF restarts fetching and guessing at the correct instruction after the branch. There are also cases where the LSU can make predictions that a load is not influenced by a previous store, and later determine that is was wrong. In a similar fashion to a branch unit mispredict, the LSU may request a Read After Write (RAW) flush. In that case, all instructions associated with the load are flushed, and the GPC requests that the ICF start again at the previously failing load.

As stated above, all memory operations decoded by the IDR are first sent to IXU to schedule the uop execution based their input operands being available. They are then sent to the LSU in an out of order fashion. LSU must handle the operations such that the ARM memory ordering rules appear to have been followed. This is very complicated, and a large part of our design is geared to giving the load store unit as much leeway as possible to do operations in a out of order fashion, but to appear to all observers to have met all of the ARM memory ordering rules. Much more on that later. Suffice it to say, when a load needs to take 100's of cycles to get data all the way from DRAM, we want to get that request out as soon as possible, and try to do as much as we can while waiting for it. A fetch that hits in the L1 is done in 4 cycles. A fetches that misses to DRAM may take 1000's of cycles. Stores are designed to be much more "fire and forget" than a load. However, you can't let any other observer see your stores until you know you actually did it. Once that has occured, the LSU fires a store request to the Level 2 Cache (L2C) and then forgets about it. The L2C ensures that everything outside of the processor can operate in a pipelined (with snooping) fashion. Stores are hard, but how loads are performed dominates the performance of a high end processor.

## Stages

OOO processors have various named stages for the process of converting instructions to uops, executing them, and putting things back in order

- Fetch. As instructions are sent from ICF to IDR and put into a Fifo. As they are transferred across the interface, they are said to be fetched.

- Confirmed. A certain amount of "overfetch" occurs. Icf can find previously undetected branches in the fetched instructions and cancel them before IDR actually does anything with them. Our design allows cancelling for two cycles after fetch. After two cycles, they are said to be confirmed.

- Allocated. Confirmed instructions in the IDR fifo become allocated when the IDR is ready to process them.

- Translated. Allocated instructions are translated into uops.

- Renamed. Translated uops need their logical destination registers mapped to unused physical register resources, and their input logic registers mapped to the correct previous physical destination registers.

- Dispatched. Renamed uops are dispatched to schedulers.

  - Issued. uops in IXU and FSU schedulers are issued to execution hardware when they think they will have all of their resources available.

  - loads and stores issued from IXU can be considered to be dispatched to schedulers in LSU

  - Lsu schedulers issue load and store uops to load and store execution pipes

- Sleep. A uop that cannot yet issue for some reason is said to be put to sleep.

- Wake up. When a uop in as scheduler thinks it has all of its input operands ready, it becomes schedulable. This process is termed "waking it up". This makes the uop schedulable.

- Issue. An awake uop is issued to an execution hardware pipeline.

- Cancelled Issue. An issued instruction can get canceled in the several cycles of travelling down the execution pipeline when the scheduler, if it was awoken by accident. It goes back to sleep in the scheduler.

- Recycled. If the "execution pipeline" is the LSU, there is a further mechanism besides Cancelling for doing uops multiple times.. When uops travel down the LSU execution pipe they are expected to complete, but there are many cases where they might not. For instance, a load could miss in the L1 cache. If so, it is placed in the Load Order Buffer (LOB) and "recycled" at a later time. Uops executed in the LSU may be recycled multiple times.

- Done. A uop reports that it is done to the GPC in a completely OOO fashion once it has travelled successfully down an execution pipe. In FSUs case, it can actually signal done "early", if there is nothing but pipelining delays left to occur.

- Commit. Gpc tracks the OOO dones. Once all of the uops comprising the oldest instructions in the machine are done, GPC reports Commit for those uops back to the units, so they can begin Retirement. Commitment indicates that the uops are allowed to make permanent changes to the processor's logical state.

- Retire. Committed instructions can free up resources at this point, and once the have made their changes to the processor's logical state, they are said to be retired. For both Branches, and Stores, this process can take a variable amount of time.

## Frontend

The purpose of the frontend of the pipe is to produce a stream of instructions along a proposed speculative path, and feed them to the backend which executes them. The frontend works without any real knowledge of the state of any of the architected registers. It does not know the value of the Flags, the Gprs, or the Vector registers. It only knows the instructions themselves, and gets trained by corrections supplied by the backend.

- Icf's BPU makes guesses about possible cachelines to fetch. It does this by having some arrays that indicate what fetches followed other fetches in the past. If the “current cacheline fetch” is not in the table, it assumes it should fetch sequential cachelines.

- Icf's BPU makes guesses about possible branches those lines contain, this informs the future decisions about what cachelines to fetch. The BPU may discover that its guesses about branches are inconsistent with the series of cachelines it has started, and may flush some of those requests to make them consistent.

  - For example, the BPU's Next fetch prediction may say "just keep fetching sequentially", but the Branch Target Buffer may say, hmm, I think the third consecutive sequential cacheline has an unconditional branch in to X. So, keep fetches 1-3, but throw away everything after 3, and restart guessing the series of cachelines we may need starting at address X.

  - How did the BPU decide there is a branch in a particular cacheline at a particular slot? Initially, it doesn't think there are branches in any cacheline. It gets taught. It gets taught by the I L1 logic about the presence or absence of branch instructions in the cacheline, and it gets taught by the GPC about the correct direction to take on conditional branches or target addresses of the indirect branches. The IL1 itself constructs all target addresses of direct branches, so those are only "taught" by the IL1 logic, not the GPC.

- Icf's BPU places an ordered list of cacheline requests into the ICF Front End Queue (FEQ), information about the guesses that were made are stored in the Branch Information Buffer (BIB). There is one location in the BIB for every position in the FEQ.

- Icf's L1 logic processes the items in the FEQ in order, simultaneously starting lookups in the L1's local Tlb, the L1 instruction cache, and the L2 instruction cache.

- The L1's local TLB is pretty small; it has 64 total entries, done as a 16 x 4 set associative array. We support a total of 8 different pages sizes. The base page size can be 4k, 16K, or 64K. The 4K pages can be grouped into 2M, or 1G huge pages, the 16K can be grouped into 32M huge pages, and the 64K can be grouped into 512M or 4T huge pages. Bits 15:12 of a virtual address are used as the set index, so pages greater than 4K may have to be duplicated in more than one set. A 64K or larger page might have to be duplicated in all 16 rows to be able to access all 64K. This effectively makes our page sizes 1/16th the ‘real’ size as far as L1 tlb misses are concerned. To make up for that loss, the path to the tlb in the I MMU is very fast.

- Icf's L1 logic makes its requests in aligned, full-cacheline increments. The interface to the IDR is only 8 instructions wide, so the IL1 may "hiccup" once to process both halves.

- Icf's L1 logic either cancels the main TLB and L2c requests, or lets them proceed based on whether the data hits in the L1Tlb and L1 as appropriate

- Icf's L1 logic then compares the actual half cachelines to the BPU's guesses about the full cachelines using the data from the L1, (or the L2 fill), and information about the guesses stored in the BIB. If they are incompatible, the BPU is flushed, all entries younger that it in the FEQ are flushed, and the series of cachelines predicted is restarted.

  - For example, the BTB may have predicted an unconditional, direct branch to address X will be found at the 5th instruction in the half cacheline. However, the cache line data may actually have no branch there, a different branch, or a branch earlier in the half cacheline. This is the ONLY way that the BPU learns where the branches are. When it makes a prediction (initially no branches anywhere), it will get corrected by the Branch Target Correction (BTC) logic. The BTC logic is a small subset of an instruction decoder that the I L1 uses to gain information about the actual instructions in the cacheline. It decodes all 8 instruction in the half cacheline in parallel. The BPU will eventually learn where the branches are in the program from BTC corrections.

- The Branch Target Buffer (BTB) logic in the BPU is the structure that is used to remember information about the location of taken or possibly taken branches. If a conditional branch is NEVER taken, it may not ever create an entry. The BTB can record the location and target addresses of branches that have been taken in the past. The BTC logic communicates with the BTB.

- Icf's L1 logic delivers instructions, and information about their addresses and some of the guesses to the IDR which puts them into fifos.

- Part of the information delivered to the IDR is predecode information. This is done on a "per instruction" basis. In other words, 32-bits of instruction go into some logic, and N bits of predecode come out. The predecode is not "stateful". No information about any other instruction before or after it is part of the predecode process.

- Our translations from instructions to uops is relatively simple. Instructions fall into the following categories, Fusible, Single, Double, Triple, or Isolate. A Fusible instruction can translate into 1 uop, or 1/2 uop (fused with the following 1/2 uop instruction). A Single translates into exactly one uop, a Double translates into exactly two, a Triple into exactly 3, and an Isolate into 4 or more. The predecode information from ICF contains enough information to classify the instructions into those 4 categories. If the instruction is marked "Fusible", the predecode information will assist the IDR in determining if consecutive instructions are in the fusible class, and if consecutive instructions are fusible with each other.

- A variable length instruction set like x86 can use as many bits as they want to make an immediate field. In a fixed 32-bit instruction set, there are must be less than 32 bits in an immediate. In Arm V8, the biggest immediate field is 25-bits in an unconditional branch instruction. Mov immediate has even less. If you want a 64-bit, arbitrary value immediate, it would take 4 instructions. That is the major motivation for fusing instructions. We fuse at most 2 instructions at a time. That strikes the correct balance of complexity and efficiency.

- Instruction decoding is done in three steps.

  - The ICF does some pre-decoding on a per instruction basis. All instructions sent from the ICF to the IDR have that additional 8 bits of predecode information passed with them. This predecode helps IDR with alignment and fusion calculations.

  - The second stage of decoding is in the IDR and is called the ALG. It looks at pairs of adjacent instructions. If the predecodes indicate that the pair of instructions might be fusible with each other, the 64 bits are looked at together to determine if they really are fusible to each other. The output of this second stage, along with the predecodes determines the routing of up to 5 consecutive instructions into the final stage of decoding. In cases where an instruction produces more than one uop, the instruction will be replicated multiple times going into the XLT stage.

  - The third stage is called the XLT stage. No more than 4 uops can be produced in a single cycle in the XLT stage. The 4 uops are in "lanes" numbered 0-3. In some cases where less than 4 uops are produced in a cycle, gaps may be inserted in the lanes used. For example, for three uops, lanes 3,2, and 0 might be used, with lane 1 marked invalid.

- The decoders produce uops. A uop has an uopcode, and a ton of information about the instruction. (plural in the case of two instructions that have been fused).

  - Does it write a general purpose register?

  - What logical gpr's does it use for sources?

  - uses FLAGS?

  - sets FLAGS?

  - executed by IXU, FSU, or IDR itself?

  - etc

- the logical gprs, vector registers, and flag registers are renamed into a greater number of physical registers for each of the three categories. This is the IDR REN stage.

- A UOP can read at most 3 physical registers, and write a single physical register, with one exception, load pair (LDP). More about load pairs later. There are many restrictions where the "at most" is restricted to smaller numbers and combinations. It can write either a GPR or a VEC register, but not both. It can write the FLAGS at the same as a GPR or VEC register.

- Uop “lane rebalancing” is done. There are 4 lanes of uops, and there is some execution hardware that is tied to the lanes or groups of lanes that they came from. The IDR attempts to balance the load on those units by “swizzling” the lanes, or otherwise modifying parameters about the required execution hardware.

- The entire pipeline from the ICF guessing a sequence of instruction fetches to the production of uops and the renaming of logical registers into physical registers is referred to as "the frontend" of a superscalar processor. The logic after that is called "the backend". So, the frontend produces uops ready to be executed, and the backend executes them.

- The front end operates in a "speculative, but logically sequential" fashion./

- The uops delivered to the backend have quite a bit of dependency information built into them. Once a uop has all of its dependencies resolved, and there are sufficient resources available in an execution unit, it can be dispatched to an execution unit.

## Backend

The purpose of the backend of the machine is to execute the uops supplied by the frontend. As an optimization, the backend can process things highly out-of-order (OOO). It is able to do this through the magic of using schedulers and dependencies. As the frontend delivers the uops, they go into schedulers. The schedulers are constantly looking for uops that have all their dependencies resolved, and also have the execution hardware available to execute the uop. When both of those things are true, the uop is issued to an execution unit. The issuing may be "just in time". In other words, the dependencies and execution hardware might actually not be completely ready, but the backend knows that by the time the uop will actually need the resource it will be available. For example, when a floating point unit does a (A*B)+C operation, the C is not needed on the very first cycle of execution. This multiply and then add is called a FMADD. If the C operand needed by the FMADD will be available by the time that it is needed as a result of some other uop, the FMADD can issue.

- We have 3 units that can schedule and issue uops. The Integer eXecution Unit (IXU), the Floating-point / Simd Unit (FSU), and the Instruction DecodeR (IDR). The IDR is a special case since it handles uops that have no dependencies, and execute in 0 cycles. Think No Operation (NOP). Because of this, the IDR does not need a scheduler.

- Both the IXU and the FSU have complicated multi-level schedulers. It is very dificult to design generic hardware that can look at all outstanding uops and pick the very best one, so nearly all modern processors have complicated multi-level schedulers.

- the cycle after selection, the register files and flags are read from the appropriate physical locations if the source value is not being used "just in time"

- the initial source values are sent to the appropriate execution hardware with other uop information to begin the actual execution of the uop.

- if the uop was a branch uop, the guesses made by the frontend are verified. If incorrect, all newer uops will be flushed from the system, the frontend will be informed, and the frontend will be restarted at the correct place.

- when the uop is finished with execution, a done indication is sent to the Global Pipeline Controller (GPC).

- The GPC is constantly looking at the oldest remaining uops, and finding out if they are being marked done this cycle. If so, the uops are "committed". Up until this point, the uops have changed physical registers that no "committed" version of a logical register is mapped to. Until commitment, the change is not architecturally visible. The commitment process makes the effect of the uop architecturally visible, and releases the hardware resources that were used to describe the uop.

### Renaming

A critical aspect of OOO processing is renaming. There are 32 logical GPRs in the ARM v8 instruction set. One can claim there are 35 due to how Arm treats the Stack Pointer. All four "execution levels" have their own Stack Pointer. In an instruction, the use of X31 can mean either the zero register, or the current stack pointer depending on the instruction. We map X31 to either 31, 32, 33, or 34 based on the current execution level. We also support 3 hidden GPRs that are only used as temporary storage in multi-uop expansion of complicated instructions. So, we claim to have a total of 38 logical GPRs. We have a total of 80 physical register locations in 2 partitions, for a total of 160 physical registers. We map the 38 logical registers on to the 160 physical registers. At the beginning of time, the 38 logical registers are mapped onto the first 38 physical registers. The rest of the physical registers are put on an "unused" list. Every time an instruction is translated into its constituent Uops, all of the source logical registers are translated using the then-current speculative Logical→Physical Gpr mapping. The destination is assigned to a currently unused physical register. The current speculative Logical→Physical GPR mapping is updated to indicate that the logical destination register is now a different physical register. We actually do this for 4 uops worth of instructions in parallel, but the hardware must take into account the updates from earlier instructions destination onto later uop sources. The execution units then look only at physical addresses of the GPRs. Even though the Uop might have been from an add, and X0 = X1 + X2, the uop will be completely in terms of the corresponding physical register. Say the very first instruction translated was ADD X0, X1, X0. At the beginning of time, the two sources will actually be in physical registers 0 and 1. The rename will rename X0 to be physical register 0, and X1 to be physical register 1. It will rename the output register to be physical register 38, the first unused physical register. Until some other instruction sets "X0", the rename hardware will map X0 to physical register 38. This renaming allows hardware to watch for writes to physical registers, and mark off when all of the sources in an instruction are now valid. When they are all valid, the instruction is then issuable. Our method of doing OOO is different than the original "Tomalsulo's Algorithm" for out of order execution in two major ways. The use of reservation stations, and how the "Reorder Buffer" is used. In a system with reservation stations, there are one or more sets of reservation stations tied directly to pieces of execution hardware. When an instruction is decoded, a piece of execution hardware with at least one reservation station available is chosen, and any of the currently available input operands are sent to the unit. If one or more of the input operands is not yet valid, a token is placed in the reservation station that indicates which other reservation station has the operation that will write it. When Uops complete, they broadcast who they are and what data they have, then the reservation stations that are awaiting notice have their tokens replaced with the data. So, in a classical reservation station model, the input data for an operation arrives in dribs and drabs. The equivalent to the scheduler needs to hold all of the input data. Instead, we hold the physical address of the input operand. When all of them are ready, we schedule the physical register file read and read all of the input operands for the Uop at the same time. The other half of the major difference is in the use of the Reorder buffer. In the original Tomasulo Algorithm, all register file writes are put into the reorder buffer in an OOO fashion as the Uops complete, the data is held there until it is the oldest instruction in the machine, and then the data is physically written into the logical register file. We don't even have a logical register file. We only have the physical register file, and several different Logical→Physical mapping vectors. When an instruction completes in our microarch, the data is not moved. It remains in the physical register file wherever it was written into, and the Committed Logical→Physical mapping vector is simply updated. So, our schedulers and Rob deal with pointers to the data, not the data itself.   
   
 Besides the GPRs, we also rename the FSU's 32 vector registers, and the IXU's single flag (condition code) register. Similar to the GPRs, there are 6 additional temporary VEC registers, for a total of 38 logical VEC registers. We have 128, 128-bit physical registers for the 38, 128-bit vector registers, and 48, 4-bit physical registers for the single 4-bit flag register.

### Partitions and scheduling.

Looking at modern OOO processors, all have a big collection of execution hardware fed by some scheduler(s). This is a very hard problem to do well in high-speed logic. Altogether, we have 192 Uops that can be outstanding. This is termed the OOO window. Each has a set of dependencies like which physical GPRs are needed, and “has the uop that produces them executed yet”. Reports are coming in from the execution units and updating the entries. Something has to then scan the entries and make a choice about which of the 192 entries we want to start next for all of the available execution hardware. This is a portion of the design where every different processor micro architecture makes a different set of tradeoffs. Solving the problem perfectly is not possible running in the multi-gigahertz frequencies. All solutions to this problem require some type of slicing and dicing of the problem into smaller more manageable pieces. The first major "dicing" is that we have first split the problem into 2 halves. The Floating point/SIMD unit has scheduling hardware for the instructions that manipulate the Vector registers, and the Ixu has its own scheduling hardware for the instructions that will manipulate the General Purpose Registers, Special Purpose Registers, and all loads and stores. This is still not enough subdividing of the problem.

### FSU schedulers

The schedulers in the FSU are simpler, so I'll talk about them first. There are two nearly identical schedulers, X and Y. Each of the two schedulers can hold up 24 Uops. So, we can have at most 48 FSU uops waiting between when they are dispatched from IDR to when they are issued to actual execution hardware. At instruction decode time, the uops that will be produced from an instruction will be classified and sorted. If they are uops destined for the Floating Point/SIMD Unit (FSU), they are further split into X pipe or Y pipe and dispatched to the appropriate scheduler. A Uop will remain in the scheduler from dispatch through issue, plus a little more. In our architecture, it is possible for a scheduler to issue an instruction, and then figure out it was wrong to have done so. So, we have to not only wait until we issue, but we have to issue and be past any time where we could decide we were wrong. The execution hardware under the X and Y pipes is nearly identical. There are some minor differences between them that we can gloss over for the moment. There is one major difference between the X pipe and Y pipe hardware. The Y pipe is the only FSU hardware that can communicate with the LSU to be able to do load and store operations. Even though that is pretty major, we are going to gloss over that as well.

At dispatch time, the instruction decoder looks at the uops it is producing and uses some algorithm to determine which of the two schedulers to use. As stated above, the X and Y execution hardware is not identical, so if this operation needs something that falls into the differences, then the scheduler assignment is forced. Beyond that, there is an algorithm to balance the pipes. Once assigned to a scheduler, the uop is never "rebalanced" to the other scheduler, even if the one scheduler happens to backup and remain full, and the other can drain. Fullness can affect the decision done at dispatch, but once picked, a uop can never be switched to the other scheduler. Again, there are some obvious corner cases that would make schedulers that could rebalance better than fixed assignment schedulers. However, we still haven't subsetted the problem enough to be tractable in 3 GHz hardware.

The next level of slicing the problem is to treat the scheduler in terms of Groups and Entries. The 24 entry schedulers are broken down into 8 groups of 3 entries. Why is this? In a normal mix of instructions that are being sent to the schedulers, most instructions will actually be ready to schedule as soon as they arrive. Some will have serial dependencies on other instructions and need to hang around longer. Some instructions will be dependent on something like a load all the way from DRAM, and remain in the scheduler for hundreds of clocks. What would you do with the holes? If you let the dispatch fill in any empty entry in the scheduler, there would be no order at all between adjacent entries. Sure, you could design hardware that could look at 24, 9-bit Rob entries and find the oldest one, but you couldn't get that to run at 3 GHz. Perhaps not even 1 GHz. Emag solved this problem by using a smaller number of entries (8 to 12), and not requiring it to pick the oldest on the very first cycle it became ready. If several Uops were ready at the same time, it would take the oldest from the last cycle, or even two cycles ago. One of the schedulers had an even worse kludge. It was a scheduler that needed to pick two entries every cycle. Instead of the two real oldest entries, it actually picked the nearly oldest and the nearly youngest as the best approximation it could do. The point being, scheduling is hard to do perfectly, so approximations must be made. Our grouping scheme is a different approach to solve this difficult problem. The 8 groups do not have a predetermined fixed relationship to each other. At any time though, we know the order of any group with respect to the others. When we dispatch, we first pick a completely empty group and fill it sequentially. The first one we pick will then be the oldest group. When it is full, we grab the next empty group and start filling it in order. So, the entries within a group are known to be in order, and we also know the order between groups. Eventually, the entries in the group are issued OOO, and get past the "Oops, I should not have issued" point on all of the instructions in the group. Then, the entire group is released as being empty. Only when all 3 entries have been used can the group be reused. Yes, it is possible that our 24 entry scheduler can be full when it only has 8 entries left in it in the degenerate case.

Btw, the total order on 8 groups can be done with a 25 bit age matrix, doing the pairwise comparison of one group to another. See the FSU spec.

There are some fine points I have glossed over here. The X and Y schedulers also schedule the interactions with the LSU unit, using hardware called the XZ and YZ execution pipes. More about that later.

### IXU Schedulers

The bulk of the schedulers are actually in the IXU. All of the integer instructions, all of the loads and stores, all of the branches, and all of the system level instructions go through the IXU. Additionally, much of the communication between the FSU and the load/store unit go through the IXU. Altogether, the IXU has 6 schedulers holding 21 uops each, all organized as 7 groups of 3. The 6 are organized as 2 partitions of 3 schedulers each. The two partitions are very nearly symmetric. As stated earlier, the decoder produces up to 4 uops in every cycle. The first 2 uops are handled by partition0, and the second 2 are handled by partition1. This is the last level of slicing and dicing the scheduling problem to make it tractable. We split FSU/IXU, we split by execution pipelines, we split by groups, and now we split by partition. We have a total of 174 uops ( 2*24 in FSU, 2*3*21 in IXU) worth of scheduling organized into 8 separate schedulers as follows:

1. FSU Scheduler x, 8 groups, 3 entries, Pipe X + Pipe XZ (picks one of each every cycle)

2. FSU Scheduler y, 8 groups, 3 entries, Pipe Y + Pipe YZ (picks one of each every cycle)

3. IXU Partition0 Scheduler a, 7 groups, 3 entries, Pipe A0 (includes branches)

4. IXU Partition0 Scheduler b, 7 groups, 3 entries, Pipe B0

5. IXU Partition0 Scheduler m, 7 groups, 3 entries, Pipe M0 (only loads and stores, can pick one of each)

6. IXU Partition1 Scheduler a, 7 groups, 3 entries, Pipe A1 (includes branches)

7. IXU Partition1 Scheduler b, 7 groups, 3 entries, Pipe B1

8. IXU Partition1 Scheduler m, 7 groups, 3 entries, Pipe M1 (only loads and stores, can pick one of each)

Having 8 separate small, 2-level schedulers that IDR picks at dispatch time make the scheduling problem tractable.

The determination of which scheduler to place any particular uop into is made by the IDR at dispatch time, and does not change. The only way to leave a scheduler is to either be issued to the execution pipeline under the scheduler, or for GPC to inform the schedulers to flush them. Many of the schedulers do support provisional issue as stated earlier. We sometimes issue based on an early indication that we might have all the inputs and resources for an Uop only to find out within the next two cycles that we were wrong. This is especially difficult in the IXU schedulers since a provisional issue may actually cause another provisional issue since the dependency chains are so short. The FSU shortest latency operations are long enough that a provisional issue can never cause a provisional issue.

In this micro architecture, remember that the LSU is considered to be a child execution pipe of the IXU. The IXU does most of the heavy lifting on scheduling operations for the LSU. The LSU then saves information about the loads and stores that have been requested by the IXU, and does a limited amount of rescheduling them based on memory access ordering rules, MMU translations, and actually handling the variable delays involved with a heavily cached memory subsystem. The IXU supplies the addresses, data, and ordering information, then the LSU performs the operations to match the requests.

## Rob/Lob/Sob/Bob and their friend Bib

In an out of order machine, we need to track information about the various instructions and uops. We have 5 major structures to do that. In a perfect world, we could assign an identifier to each unique instruction, and a separate identifier for every uop, and save whatever information we needed in some sort of magical, infinite storage. When we are running tests in Verilog simulations, we can do that. For each instruction that the frontend ICF sends to IDR, we assign an Instruction Fetch Universal Identifier (IFUID) and create a data structure to hold information about that instruction. For every Uop the IDR produces, we assign a Uop Universal Identifier(UUID) and create a data structure for that. Since we are never going to simulate more than 2<sup>64</sup> instructions or uops, a longint is a big enough identifier to be "infinite". Obviously real hardware cannot do this. Even 64-bit counters would rollover, and where would we put all of the data structures? Instead, real hardware has to use much smaller counters, manage the rollover, and be very selective in what data to save. These structures are the Rob, Lob, Sob, Bob, and Bib. The "ob" stands for "Order Buffer". The "ib" in Bib, stands for "Input Buffer". All of these structures are relatively small compared to 2<sup>64</sup>.

### Bib

The Branch Input Buffer is at the top of the pipeline in the Icf, in parallel with the Front End Queue. It contains only 64 entries. It definitely does not cover every instruction. It contains information about the BPU's predictions on an entire-cacheline prediction basis. Every cacheline request to the L1 that the BPU put in the FEQ has a BIB entry. One can consider it an extension of the FEQ entry itself. The entry goes into the BIB at the same time as the entry is written into the FEQ. This is the least interesting of all the IDs that are used to manage ordering in the design. The "namespace" of the BibId does not make it out of the Icf. The entry contains information about how the BPU made the prediction. If the L1 determines that the prediction was so bad, it doesn't even match the cacheline that was fetched, the L1 does a Branch Target Clear (BTC) and gives the BPU the FEQ position and the BIB position of the failure. The BPU can use the two to improve the prediction to at least match the cacheline. If the L1 decides that the prediction does match the cacheline, it leaves the entry in the BIB. Eventually, the BIB data gets transferred to the BOB.

### Bob

The next in the hierarchy of identifiers and their associated data is the Branch Order Buffer (BOB). It is a little bit of a misnomer. It handles more than Branches. In the original EMAG1 core (aka piranha), this information was about a Sequential Instruction Run (SIR), and the information saved was stored in a Branch Checkpoint. Regardless, every OOO processor wants to minimize the amount of storage needed to describe "where is this current instruction in the Virtual Address (VA) space, and how did I get here?" It is inefficient to save all of the information on every instruction. So, instead we save information only periodically, and then instructions keep track of a much smaller offset from the last data point. Some random integer instruction 5 instructions after a taken branch does not really need a whole 64-bit VA for knowing its Program Counter (PC) value. It can point to a BOB entry that describes the last taken branch and say, I am 5 instructions past the target address. We have a total of 64 BOB entries to cover the 192 Uops that we can have in flight. We use a 7-bit identifier. Why 7 bits when 6 bits would do? We add an additional bit, normally termed "color". So, the Bob IDs (in binary) 000_0000 and 100_0000 actually point to the same BOB location, but have a "different color". Why is that useful? We use the BOB IDs in a circular fashion, starting at zero, and working all the way around to the last BOB, 11_1111, we then wrap back to entry 00_0000. By adding a "color" bit we can get a little "hamming distance" between the entries. This is most important in distinguishing the empty and full cases. Switching to hex instead of binary, we use the entries starting at 0x00, up to 0x3f, and from 0x3f, we go one to ID 0x40 then up to 0x7f, before wrapping to ID 0x00. If we know that our "writing pointer" is at 0x40 and the "reading pointer" is at 0x00, we are FULL, all 64 entries are in use. Full is when the Color bit is different, but the bottom 6 bits are identical. Empty is when the color bit is the same, and the bottom bits are identical.

Why is the name Branch Order Buffer a bit of a misnomer? Because if we have enough sequential instructions, we allocate a BOB entry just to keep the "offset from the last BOB" to be a reasonable number of bits.

Throughout the backend, information about instruction locations are computed by specifying a 7-bit BOB id, and a 5 bit offset. We create a BOB entry no more than 32 instructions away from the last. In our simulation world, we have a full 64-bit IFUID, and an arbitrarily long data object for every instruction. In the hardware, we have a 7 bit ID, and only have a fixed number of bits per entry, and only actually have entries for those instructions that absolutely need them.

### Rob

If BOB is the rough hardware equivalent to an identifier and data structure for every instruction, then the ReOrder Buffer is the equivalent for Uops. Every Uop in the machine is given the next "sequential" Robid. We allow 192 outstanding Uops. This would require 8 bits. We add a single bit of "color" to make a 9-bit ID. The Ids go from 0x000 to 0x0bf, and then "jump" to 0x100 and go up to 0x1bf. 0xC0 is 192 decimal, which is why we jump at 0xbf. Every uop that the IDR produces will get a RobId, and there is a 192 entry Rob in the GPC that stores information about the Uops. When we dispatch a Uop to a unit, we will send the assigned RobId with it. The hardware will talk to each other based on this ID. When execution hardware completes an operation, it will tell GPC it is done using the RobId. When the ICU asks the LSU to do a load or a store operation, it will include the RobId. The whole backend communicates to amongst itself talking about uops by their RobId. Since RobIds are assigned by the IDR in order, and we have the extra color bit, we can actually compare RobIds of two different Uops, and know their relative orders. That comparison would not be possible without the additional color bit.

### Lob and Sob

The Load Store unit uses 2 additional structures for Ordering and data storage purposes. It would be theoretically possible to just use the ROB for this information. However, Loads and Stores need different information from each other, and both need information that normal Ixu and Fsu rob entries would have no use for. Additionally, the number of Lob and Sob entries have direct requirements on actual hardware. For example, as will be described below, stores are done into a store forwarding buffer (SFB), not into the D cache. This allows them to speculative write their data into the SFB, without actually changing the cache, or even getting the cacheline exclusively. Due to coherency rules, when a processor does a write, it first has to make sure that no other processor anywhere has that same cacheline. Writing the stores into the store forwarding buffer instead of the cache allows the appearance to this processor that the write has occurred, but delays the right to the cache until it has REALLY occurred. Every load from this processor that is logically after a store from this processor must look through all stores that are sitting in the store forwarding buffer. It is important that it looks only at the stores that are logically before it in the instruction stream. It really only has to looking at stores whose cacheline addresses match. This represents a big Content Addressable Memory (CAM). The load address must be compared to all of the store addresses, and ordering information must be applied. We use only 40 entries in the SFB, and actually organize them on 64-bit boundaries, not 512-bit cacheline boundaries. Using only 40 SFB entries means we want 80 SobId's. In a similar fashion to the small SOB namespace, we have a 64 entry LOB, needing a 7-bit LobId. Like the SobId, the LobId carries no more information than the RobId does. Theoretically, one could use the Rob instead of the Lob. But again, having only 64 entries simplifies comparisons. There will be more on the LOB and SOB in the next section.

One fine point on the SOB. A store reports to the GPC that it is "done" as soon as the write data and the write address are given to the LSU by the IXU and the SOB is updated. This makes the store visible to loads from this processor. However, the process to actually write the cache does not even begin until the GPC determines that the Uop with the Oldest SobId is the oldest uop in the machine. It tells LSU the store is committed to be done at that point. However, at that point, it STILL hasn't update the cache yet. Once the LSU transfers the store to the L2, the store is said to have been retired. It is only at that point that the SOB entry can be reused. So, if we had infinite hardware, we COULD store all of the SOB information in the ROB, but then we would need even more ROB entries because the "SOB" information in the entry still is the responsibility of the LSU until the L2 has accepted it at retire time. If the L2 is backed up, there can be a significant amount of delay between the store commitment (is the oldest uncommitted uop), and the store retirement (the L2 has accepted ordering responsibility for the store data)

Back to the big picture. As stated above, the use of the 384 RobIds does put a total order on the Uops in the machine. There is no ambiguity; given two RobIds that can be in use at the same time, it can be determined which one is logically older by comparing their ROB IDs. Any particular Rob entry will have a Lob and Sob ID as well. Every load instruction uses the next "circularly sequential" LobId, and every store uses the next "circularly sequential" SobId. If not a load or a store, the Lob and Sob IDs don't change from one rob entry to the next. The Lob and Sob Ids give no new information about the relative ordering because the RobId already presented a total ordering of the Uops. However, using the LobId or SobId can make some necessary comparsions simpler, requiring less hardware. It also makes relative comparisons of the relative ordering of loads and store easier. Every load can easily determine which Store Forwarding locations should affect it by comparing sobids only. Additionally, it allows us to use an actual LOB structure with only 64 entries and a SOB structure with only 40 entries to hold the additional information that a load uop or a store uop needs without requiring every ROB entry to have enough room for all of it.

## Loads and Stores

In all computer architectures, there are some common problems in executing load and store operations. Different architectures have different views of ordering rules. Memory ordering rules define the order in which loads and stores must be seen by the uniprocessor itself, and what order the loads and stores from this processor must be seen by other processors in the multi-processor system. Even within a single architecture like Arm v8, there may be different load and store instructions that have different ordering rules. Much of the complexity in load/store units is in handling ordering rules in an efficient manner. The ordering rules in different architectures vary along a pretty large spectrum. On one end is IBM mainframes and the X86 architectures. Both grew up in "uni-processor" worlds and have only evolved to handle multi-processing. At the other end of the spectrum was the DEC ALPHA. It was designed with multi-processing and ultra-high performance with simple hardware from the very start. The simplicity of the Alpha hardware pushes almost all ordering back on to the compiler. In the very loose ordering rules in an Alpha, the loads and stores in a single processor are not even guaranteed to appear in order unless the exact same addressing mode and registers are used for the load that a previous store should match. The Arm architectures lay somewhere in the middle of the spectrum.

The complexity arises due to three things. One, the desire for Out Of Order execution to take advantage of doing something from later in the program when the current instruction cannot complete. Two, the desire to limit the required communication between cores in a multi-processor environment. Three, limit additional program complexity to handle when you really need to have operations in a specific order.

Load and store operations have two subcomponents, address generation and the actual memory operation. In all cases, the address generation portion must be performed first. You need to know where in memory the operation is going to be performed. In our microarchitecture, the Integer Execution unit performs the address generation calculation portion. There is a specialized scheduler and specialized execution hardware in the IXU to perform these functions. In other micro architectures, the load store unit performs its own address generation. Once the Address(es) are calculated, they are sent to the load/store unit. For a load, the location of the physical register for the result is sent with the address. For a store, the store data is normally sent along with the addresses.

### Address Generation versus Data Phase (Integer LOADS)

The ixu is responsible for scheduling all of the register reads for doing LSU operations. As stated above, a load or store has the two separate components. The AGU portion and the memory operation portion. Most Load operations can combine the AGU and Data Phase as a single micro op. The AGU for loads is allowed two register reads, so it can fetch a base and index register. The Data Phase does not need a source register, only a destination register. As an optimization, the Load Pair instruction is the ONLY uop that can have 2 destination registers, we will ignore that again for the moment. Integer load instructions will normally have a single uop that describes the address generation, and then also information about how the load data should be manipulated before being written. In summary, all of the register reads required for loads are for the AGU portion. When the load completes, there will be destination register writes. When all of the source registers for the AGU portion are ready, the IXU scheduler can then schedule the AGU operation to its dedicated AGU alus, and forward the address, and the uop to the Load Store Unit.

### Address Generation versus Data Phase (Integer STORES)

Unlike a load, a store requires a register read for the store data phase to get the data. The store pipe is limited to only 2 register reads, just like an integer load. This means that is the AGU portion needs 2 register accesses, we CANNOT use a single uop. Conversely, if a store uses zero or one register in the AGU portion, we can use a single uop to do both parts. This is termed a SUS store, the U stands for Unified. If we require two registers for the AGU, we split the store into two separate uops. The first is termed a STore Address (STA) uop and the second is termed a STore Data (STD) uop. A Store Pair instruction is another special case. The Store Pair only requires one address register, but requires 2 data reads. This is done with a special SUS that does the address and one of the store data reads, and a second uop, termed a STDHI. The IDR decodes the integer store instruction into either a single SUS, a STA+STD, or a SUS+STDHI, and send those pieces to the IXU schedulers. Those pieces are independently scheduled and sent to the LSU. The IDR will play one more important role in this process. All the uops of an individual store instruction will be marked with the same Sob ID. If a store is done as two separate uops, the IXU can send those two pieces to the LSU in either order. The two parts are then coordinated based on their common Sob ID.
